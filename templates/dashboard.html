02 / The delivery path

One change. Six stages.

Explore how a trusted pull request becomes a public preview. These stages explain the workflow, not a current run.

WORKFLOW EXPLORER

Follow the revision,
not just the image.

Publishing a container is only the midpoint. A preview URL is reported only after the environment passes readiness checks.

  1. Start with Python 3.11. Compile the application, lint application and test code, then run the automated test suite.

    python -m py_compile app.pyflake8 app.py testspytest -v

  2. Docker Buildx builds the container and publishes three tag patterns to GitHub Container Registry. The revision-pinned PR tag is deployed, tying the preview to the requested revision.

    ghcr.io/<owner>/<repo>:pr-<pr_number>ghcr.io/<owner>/<repo>:<commit_sha>ghcr.io/<owner>/<repo>:pr-<pr_number>-<short_sha>

  3. scripts/deploy-preview.sh creates or updates preview-pr-<number>: a Linux ACI container group with 1 vCPU, 1 GiB memory, and application port 8080 by default. Only matching owned resources may be deployed or updated.

  4. Require successful provisioning, the requested image, actual FQDN and network data, and a successful HTTP GET / before publishing a preview URL. Image publication alone is not preview success.

  5. The workflow attempts to update commit status PR Preview Deployment and one in-place bot comment identified by <!-- cdd-pr-preview-status -->. Subsequent updates reuse the bot comment; failures have no success URL. Both reporting channels are attempted, and a delivery failure fails the reporting step instead of silently leaving a green run.

  6. .github/workflows/pr-cleanup.yml invokes scripts/cleanup-preview.sh when a PR closes, merged or unmerged, with deployment credentials configured. Ownership is verified before deletion; a missing resource is an idempotent success, while ownership mismatch prevents destructive action.

04 / Preview lifecycle

Temporary by design.

A dedicated place to review changes, with explicit boundaries for its entire lifetime.

01

Open. Push. Update.

A trusted PR triggers validation and deployment. Later pushes update the same PR environment. Stable same-PR addressing depends on a stable PREVIEW_DNS_PREFIX and configuration.

02

Review in isolation.

Independent PRs have separate preview environments. Review visible changes and gather feedback without treating the preview as production.

03

Close the loop.

Merged or unmerged closure triggers cleanup when credentials are configured. Ownership must match before deletion; already-absent environments are handled safely.

One PR, serialized mutations

Deployments and cleanup serialize per PR under cdd-preview-pr-<number> with cancel-in-progress: false. Separate PRs can proceed independently. This is serialization, not a durable ordered queue; workflows recheck current PR state and revision before mutations.

Preview does not mean private.

  • Run secret-bearing workflows for trusted PR code only.
  • Use dedicated nonproduction resources.
  • Previews use public, unauthenticated HTTP—not HTTPS.
  • Never include sensitive data or application secrets.
  • Azure Container Instances incur charges while running.
  • Ownership mismatch prevents destructive action.

Cleanup verifies all three ownership tags: managed-by=cdd-preview, pr-number=<number>, and preview-owner=<PREVIEW_DNS_PREFIX>.

01 / LOCAL DEVELOPMENT

Run locally

Install requirements first, then start Flask. The default URL is http://localhost:8080.

python -m pip install -r requirements.txt
python app.py
02 / CONTAINER DEVELOPMENT

Run with Docker

Build the application image, then map local port 8080 to the container's application port.

docker build -t cdd-demo-app .
docker run -p 8080:8080 cdd-demo-app
03 / LOCAL CHECKS

Validate changes

Use the same compilation, linting, and test commands as the Python 3.11 validation stage.

python -m py_compile app.py
flake8 app.py tests
pytest -v

06 / HUMAN VERIFICATION

Review checklist

Use these checks when reviewing a real preview. They are instructions, not claims about current runs.

  • Verify the revision's visible changes.
  • Check that same-PR pushes update the environment.
  • Confirm separate PRs remain isolated.
  • Verify honest failure reporting without a success URL.
  • Check cleanup after both merged and unmerged closure.
